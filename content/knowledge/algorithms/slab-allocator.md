## 문제

범용 할당기는 임의 크기를 다루려고 빈 블록을 찾고 쪼개고 합친다. 커널처럼 **같은 구조체를 매우 자주 만들고 버리는** 곳에서는 두 가지가 아프다.

- **외부 단편화**: 크기가 섞여 쪼개고 합치다 보면 아무도 안 쓰는 작은 빈 조각이 쌓인다.
- **초기화 비용**: Bonwick 은 많은 경우 객체를 초기화하고 파괴하는 비용이 할당·해제 자체보다 크다고 지적한다. 뮤텍스를 가진 구조체는 `mutex_init()` 을 한 번만 하면 되는데, 매번 할당·해제할 때마다 다시 한다.

[메모리 풀·아레나](/develop-wiki/knowledge/algorithms/memory-pool-arena/)가 "수명이 같은 객체를 통째로 반환"하는 해법이라면, 슬랩은 "**수명이 제각각인 같은 종류의 객체를 효율적으로 재활용**"하는 해법이다.

## 해법: 종류별 캐시, 그 안의 슬랩

SunOS 5.4 슬랩 할당기(Bonwick, USENIX 1994)의 구조다.

- **캐시**: 객체 종류마다 하나(예: inode 캐시). 캐시는 객체 크기, 생성자·소멸자 함수를 안다.
- **슬랩**: 캐시가 가상 메모리에서 받은 한 페이지 이상의 덩어리. 같은 크기의 **버퍼**로 균등 분할돼 있고 자체 프리리스트와 **사용 중 개수(참조 횟수)** 를 가진다.
- **할당**: 부분적으로 찬 슬랩의 프리리스트에서 하나 꺼낸다. 참조 횟수를 올린다.
- **해제**: 프리리스트에 되돌리고 참조 횟수를 내린다. 객체는 **생성된 상태(constructed state) 그대로** 두어 다음 할당 때 다시 초기화하지 않는다.
- **반환**: 참조 횟수가 0 이 된 슬랩만 통째로 VM 에 돌려준다. 시스템이 메모리를 요청할 때만(압박 시) 일어난다.

논문이 꼽는 장점은 구조에서 바로 나온다.

1. 합치기(coalescing)나 트리·비트맵 없이 **참조 횟수 하나**로 회수 가능 여부를 안다.
2. 할당·해제는 프리리스트 조작이라 **상수 시간**이다.
3. 크기별로 분리된(segregated) 저장이라 한 크기의 요청이 다른 크기의 조각을 만들지 않는다. 같은 슬랩의 객체는 같은 종류라 수명 분포도 비슷하다.
4. 버퍼가 정확히 객체 크기라 슬랩 끝의 자투리 외에는 **내부 단편화**가 작다.

### 슬랩 레이아웃과 색칠(coloring)

- 슬랩에 버퍼가 n 개 들어가면 내부 단편화는 최대 1/n 이다. SunOS 5.4 는 이를 12.5%(1/8) 이하로 제한한다. 슬랩이 클수록 버퍼는 많아져 내부 단편화는 줄지만, 모든 객체가 해제돼야 반환되므로 외부 단편화에는 불리하다(아래 실험).
- 작은 객체(페이지의 1/8 미만)는 슬랩 관리 구조를 같은 페이지 끝에 둔다.
- **색칠**: 슬랩마다 버퍼 시작 오프셋을 조금씩 어긋나게 한다. 같은 크기 객체가 모든 슬랩에서 같은 오프셋에 놓이면 CPU 캐시의 같은 줄에 몰리기 때문이다. 논문 예: 4096 바이트 페이지에 200 바이트 객체 20개(4000B) + 슬랩 구조 32B 면 64B 가 남아, 슬랩이 새로 생길 때마다 시작 오프셋을 0, 8, 16, …, 64 로 돌린다.

### 직접 돌려 본 결과

논문 예제와 단편화 특성을 모델로 재현했다.

```ts
function layout(sz: number, page = 4096, meta = 32, align = 8) {
  const per = Math.floor((page - meta) / sz), spare = page - meta - per * sz;
  return { per, spare, maxColor: Math.floor(spare / align) * align, internalWaste: (page - per * sz) / page };
}
// 400B 객체, 구조 없이: per=10, spare=96 → 내부 낭비 2.34%   (논문: 10개, 96B, 2.4%)
// 200B 객체, 구조 32B : per=20, maxColor=64 → 색 순서 0,8,...,64,0,8,...
```

- 400B 객체: 슬랩당 10개, 96B 남음, 낭비 약 2.3%. 논문의 2.4% 와 같은 계산이다(9.6B/400B).
- 200B 객체, 슬랩 구조 32B: 슬랩당 20개, 색 최대 64, 색 순서 `0,8,16,…,64,0,…`. 논문 예와 일치한다.
- 128B 객체(2의 거듭제곱), 구조 32B: 슬랩당 31개, 96B 남음. 정확히 안 맞는 크기라 색칠할 공간이 많다는 논문의 지적과 방향이 같다.

**외부 단편화 실험**: 객체 10만 개를 할당한 뒤 **무작위로 90%를 해제**하고, 통째로 반환 가능한(참조 횟수 0) 슬랩의 비율을 슬랩 크기별로 쟀다. 해제가 객체마다 독립이면 슬랩이 비는 확률은 `0.9^n`(n = 슬랩당 객체 수)이다.

| 슬랩당 객체 수 | 비워진 슬랩 | 이론 0.9ⁿ | 남은 객체 약 1만 개를 담는 데 필요한 최소 슬랩 vs 실제 점유 슬랩 |
| --- | --- | --- | --- |
| 4 | 65.4% | 65.6% | 약 2,516 vs 8,644 |
| 10 | 35.0% | 34.9% | 994 vs 6,495 |
| 50 | 0.6% | 0.52% | 202 vs 1,988 |
| 100 | 0.0% | 0.003% | 102 vs 1,000 |

슬랩이 커질수록 거의 모든 슬랩이 어딘가에 살아 있는 객체를 하나씩 붙잡고 있어 **회수할 수 있는 슬랩이 사라진다**. 논문의 "슬랩이 클수록 반환 확률이 떨어진다"는 설명을 수치로 확인한 셈이다. 실제 객체 수명은 무작위 독립이 아니므로(같은 슬랩의 객체가 비슷한 시기에 해제되면 더 낫다) 이 실험은 **최악에 가까운 모델**이다. 해제 직후 재할당이 같은 슬롯을 돌려주는지도 확인했다(프리리스트가 후입선출).

논문은 16MB SPARCstation-1 에서 부팅·스파이크·find·kenbus 를 차례로 돌린 뒤 총 낭비(단편화)를 비교해, 슬랩이 14%, SunOS 4.1.3 이 27%, 4.4BSD 와 SVr4 가 약 45~46% 라고 보고한다. 부팅 직후에는 SunOS 4.1.3(7%)이 슬랩(11%)보다 낮았고 부하가 쌓이면서 격차가 벌어졌다. 이 수치는 1994년 SunOS 워크로드 기준이므로 오늘의 워크로드에 그대로 적용하지 않는다.

## 언제 쓰나

- 같은 타입 객체를 **고빈도로 만들고 버리는** 시스템 소프트웨어: 커널 객체(프로세스·파일·소켓 구조체), 네트워크 버퍼, 데이터베이스의 고정 크기 페이지 헤더.
- 초기화 비용이 큰 객체(락, 큐 헤드, 리스트 노드가 섞인 구조체)를 재사용하고 싶을 때.
- 사용자 공간 라이브러리에서 비슷한 이름의 구조가 필요하면 풀·아레나와 비교해 고른다.

## 주의 (비용)

- **슬랩 크기 선택이 트레이드오프**다. 위 실험처럼 크면 반환이 어렵고 작으면 슬랩 관리 구조와 내부 단편화 비중이 커진다.
- 객체를 재사용하므로 **생성자가 만든 불변 상태를 해제 전에 복원**해 둬야 한다. 이를 어기면 다음 사용자가 더럽혀진 객체를 받는다. 논문의 디버깅 기능은 해제된 버퍼를 `0xdeadbeef` 패턴으로 채워 두었다가 다음 할당 때 패턴이 깨졌는지 검사해 해제 후 쓰기를 찾아낸다.
- 종류별 캐시가 많아지면 **캐시마다 부분 슬랩이 남아** 전체로는 메모리가 샐 수 있다. 사용량 통계가 필요하다.
- 이 논문은 1994년 설계로, 락을 전역 하나가 아니라 캐시마다 두어 확장성을 높인다고 설명한다. CPU 별 캐시 같은 이후의 다중 코어 최적화는 이 노트가 읽지 않은 후속 자료의 몫이다. 리눅스 커널의 현재 슬랩 계열 구현의 세부(SLUB 등)는 확인한 문서에 없어 이 노트에서 다루지 않는다. 확인한 커널 문서 페이지는 슬랩 관련 보조 함수와 플래그 정도만 설명한다.
- 가비지 컬렉터가 있는 언어에서 직접 쓸 일은 거의 없다. [GC](/develop-wiki/knowledge/cs-fundamentals/garbage-collection/)가 같은 역할을 한다. 객체 풀링도 GC 환경에서는 조심해서 쓴다.
