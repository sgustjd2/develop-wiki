## 문제

서버가 고장 나 교체하거나 복제 수를 늘리려면 클러스터의 **구성(configuration, 투표권을 가진 서버 집합)** 을 바꿔야 한다. 쉬운 방법 둘에는 모두 함정이 있다.

- 클러스터를 내리고 설정 파일을 고쳐 다시 올리면 그동안 서비스가 멈춘다.
- 새 서버가 옛 서버의 주소를 물려받으면, 옛 서버가 되살아나는 순간 투표가 하나 더 생겨 안전성이 깨진다.

더 근본적인 문제는 **모든 서버가 동시에 새 구성으로 넘어갈 수 없다**는 점이다. 서버마다 새 구성을 알게 되는 시각이 달라서, 한동안 옛 구성의 과반과 새 구성의 과반이 **서로 겹치지 않을 수** 있고, 그러면 같은 임기에 리더가 둘 생긴다. 박사논문(Ongaro, 4장)의 그림처럼 3대를 5대로 곧장 바꾸는 경우 옛 과반 `{0,1}` 과 새 과반 `{2,3,4}` 이 서로소다.

## 해법 1: 한 번에 한 대 (단일 서버 변경)

서버를 하나만 더하거나 빼면 옛 구성의 어떤 과반도 새 구성의 어떤 과반과 **반드시 겹친다.** 과반을 모든 부분집합으로 열거해 확인한 결과다.

| 변경 | 서로소 과반이 생길 수 있나 (N = 옛 서버 수, 1~7) |
| --- | --- |
| +1, −1 | 모든 N 에서 없음(안전) |
| +2 | N 이 홀수(1,3,5,7)이면 있음(위험), N 이 짝수(2,4,6)이면 없음 |
| +3 | 모든 N 에서 있음(위험) |

겹치는 서버가 하나라도 있으면 그 서버는 한 임기에 한 표만 주므로 두 리더가 못 생긴다. 그래서 새 구성을 **로그 항목 하나로 복제**하고, 각 서버는 그 항목을 로그에 받는 순간(커밋을 기다리지 않고) 새 구성을 쓴다. 논문의 규칙은 이렇다.

1. 리더가 새 구성 항목을 로그에 추가하고 평소처럼 복제한다. 그 항목의 커밋 판정은 새 구성의 과반으로 한다.
2. 항목이 커밋되면 변경 완료. 제거된 서버는 내려도 되고, **다음 변경을 시작할 수 있다.** 그 전에는 변경을 겹치지 않는다.
3. 여러 대를 바꾸려면 단일 변경을 순서대로 이어 붙인다.
4. 구성 항목이 리더 교체로 지워질 수 있으므로 서버는 이전 구성으로 돌아갈 준비를 해야 한다.

## 해법 2: 공동 합의 (임의 변경)

여러 대를 한 번에 바꿔야 하면 중간 구성 `C(old,new)` 를 거친다. 합의(선거·커밋)에 **옛 구성의 과반과 새 구성의 과반을 모두** 요구한다.

```ts
const hasMajority = (voters: Set<string>, acks: Set<string>) =>
  [...voters].filter((v) => acks.has(v)).length > voters.size / 2;
// 공동 구성: 두 과반을 동시에 만족해야 한다
const jointQuorum = (oldV: Set<string>, newV: Set<string>, acks: Set<string>) =>
  hasMajority(oldV, acks) && hasMajority(newV, acks);
```

3대 `{a,b,c}` 를 9대 `{c,d,...,k}`(c 만 공통)로 바꾸는 경우를 이 코드로 돌려 봤다.

| 응답한 서버 | 결과 |
| --- | --- |
| `{a,b}` (옛 2/3 만) | 불충족 |
| `{d,e,f,g,h}` (새 5/9 만) | 불충족 |
| `{a,b,d,e,f,g,h}` | 충족 |
| `{a,c,d,e,f,g}` (공통 서버 c 가 양쪽에 계산됨) | 충족, 6대 |

절차는 두 단계다. 리더가 `C(old,new)` 항목을 커밋(공동 과반)하고, 이어서 `C(new)` 항목을 커밋(새 과반)한다. 어느 시점에도 옛 구성과 새 구성이 **혼자서 결정을 내릴 수 없다.** 논문은 단일 서버 방식을 먼저 권하고, 공동 합의는 완전성을 위해 소개한다고 적는다. 구현에서는 투표·커밋 판정마다 "과반"을 세는 곳 여섯 곳쯤을 고쳐야 했다고 한다.

## 가용성을 위한 보강

- **새 서버는 먼저 비투표 멤버로**: 빈 로그의 새 서버를 곧바로 투표에 넣으면 따라잡는 동안 커밋이 막힐 수 있다(3대에 빈 4번째를 넣고 한 대가 죽으면 3/4 이 필요한데 새 서버 로그가 한참 뒤처져 있다). 리더가 로그를 먼저 복제하고, 따라잡은 뒤에 구성에 넣는다. etcd/raft 의 `ConfChangeAddLearnerNode` 가 이 역할이다.
- **리더를 제거할 때**: 가장 간단한 방법은 리더 이양으로 다른 서버에 리더를 넘기고 그쪽에서 변경하게 하는 것이다. 이양이 없으면 제거되는 리더가 변경을 이끌되, 자기 표는 세지 않고 `C(new)` 항목이 커밋된 뒤에야 물러난다. 그 전에 물러나면 2대에서 리더를 빼는 경우처럼 그 서버가 다시 필요해질 수 있다.
- **방해하는 서버(disruptive server)**: 제거된 서버는 하트비트가 끊겨 선거를 계속 걸고, 큰 임기 번호로 현재 리더를 끌어내릴 수 있다. 논문은 Pre-Vote 를 먼저 떠올렸지만, 제거 중인 서버의 로그가 최신이어서 Pre-Vote 를 통과하는 반례가 있어 충분하지 않다고 한다. 해법은 **리더의 하트비트를 들은 지 최소 선거 타임아웃이 안 지났으면 `RequestVote` 를 무시**하는 것이다. 리더 이양(leadership transfer)은 이 무시를 우회하는 표시를 붙여 보낸다.

## 2015 년에 발견된 버그와 수정

단일 서버 변경에는 박사논문 서술에 버그가 있었다. 서로 다른 구성 변경 두 개가 동시에 요청되고(예: 4대에서 시작) 리더 교체가 임기 경계를 넘어 일어나면, 커밋된 구성 항목이 다른 리더에게 덮어써져 데이터 유실과 영구적 스플릿 브레인이 가능했다. Ongaro 가 raft-dev 에 공지한 수정은 이렇다.

- **리더는 자기 임기의 항목을 하나 커밋하기 전에는 새 구성 항목을 추가하지 않는다.** 보통 선출 직후 넣는 no-op 이 커밋되길 기다리면 된다.
- 공동 합의 방식은 영향이 없다고 공지에 적혀 있다.

구현을 직접 하거나 감사한다면 논문 본문만 보지 말고 이 수정이 들어갔는지 확인한다.

## 구현에서 보이는 모습 (etcd/raft)

- `ConfChangeV2` 는 단일 변경(simple)과 공동 합의를 모두 표현한다. 전환 방식은 `Auto`(가능하면 simple, 아니면 joint), `JointImplicit`(joint 로 가고 빠져나오는 항목을 자동 제안), `JointExplicit`(애플리케이션이 빠져나오는 변경을 직접 제안) 중 고른다.
- 주석에 따르면 이 구현은 논문과 달리 **구성 변경을 로그에 추가될 때가 아니라 상태 머신에 적용될 때** 활성화한다.
- 적용되지 않은 변경이 남아 있으면(이미 대기 중이거나 이미 joint) 리더는 새 변경을 거절한다.
- 주석의 예: 가용 영역 3곳에 복제 3개일 때 공동 합의 없이 투표자를 바꾸면 한 영역 장애를 못 견디는 중간 구성을 거치게 된다. 공동 합의가 그 취약한 중간 구성을 피해 준다.

## 언제 쓰나

- 서버 교체, 복제 수 증감, 리전 이전 같은 운영 작업. 대부분은 **단일 서버 변경을 순서대로** 하면 충분하다.
- 한 번에 여러 대를 바꾸면서 중간 상태의 장애 내성을 지켜야 할 때(위 3개 영역 예)는 공동 합의.

## 주의 (비용)

- 변경은 **한 번에 하나씩**이다. 앞 변경이 커밋될 때까지 다음을 시작하지 못하므로, 대규모 교체는 시간이 걸린다.
- 구성 변경 중에도 과반 규칙은 그대로다. 변경 도중 서버가 더 죽으면 쓰기가 멈춘다. 2대 클러스터에서 한 대를 빼는 것은 한 대만 죽어도 진행이 안 돼 위험하다(etcd/raft 문서가 3대 이상을 권한다).
- 자동 제거 정책은 신중해야 한다. 고장 난 서버를 자동으로 빼다가 복제본이 너무 적게 남을 수 있다고 논문이 경고한다.
- 공동 합의 구현은 "과반을 센다"는 곳마다 두 집합을 확인해야 해서 놓치기 쉽다. 논문도 단일 서버 방식을 먼저 권한다.
- 이 노트는 2014 년판 박사논문, Raft 논문, 공지 글, etcd/raft 소스 주석을 확인했다. 공지 글의 반례 전체 타임라인은 다시 그리지 않았다.

## 비교

| | 단일 서버 변경 | 공동 합의 |
| --- | --- | --- |
| 한 번에 바꾸는 수 | 1대 | 임의 |
| 로그 항목 | 새 구성 1개 | 공동 구성 + 새 구성 2개 |
| 투표·커밋 규칙 | 새 구성 과반 | 옛 과반 ∧ 새 과반 |
| 구현 난이도 | 낮음 | 높음 |
| 알려진 함정 | 임기 첫 커밋 전 변경 금지(2015 수정) | 두 집합 모두 확인하는 누락 |
