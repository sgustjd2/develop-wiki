MPHF 의 정의와 PTHash 는 [최소 완전 해시 함수와 PTHash](/develop-wiki/knowledge/algorithms/perfect-hashing-pthash/)에 있다. 그 노트가 네 가지 계열을 한 줄씩만 소개한 중 **지문(BBHash)** 과 **재귀 분할(RecSplit)** 을 원논문으로 깊이 비교하는 노트다.

## 문제

고정된 키 n 개를 0~n−1 에 하나씩 대응시키는 함수를 만든다고 하자. 선택지마다 얻는 것이 다르다.

- 공간 하한은 키당 약 1.44 비트(log₂e)다. 논문들은 실제로 2 비트 아래로 내려가는 방법이 드물었다고 설명한다.
- 키가 수십억 개면 **만드는 데 필요한 메모리와 시간**이 공간만큼 중요하다. 구조는 작아도 만들 때 RAM 이 구조 크기의 몇 배 필요하면 쓸 수 없다.
- 룩업은 주로 캐시 미스 횟수로 정해진다. 층이 많거나 트리를 따라 내려가면 느려진다.

## 해법

### BBHash: 층층이 충돌을 미루는 비트 배열

저자들은 오래된 간단한 아이디어(Müller 등의 지문 기법)를 다시 들여다보니 만드는 시간과 메모리에서 경쟁력이 있다고 주장한다.

1. 층 0: 크기 `γ·|F₀|` 의 비트 배열 `A₀` 에 모든 키를 해시해 넣는다. 한 칸에 **키가 하나만** 떨어진 자리만 1 로 표시하고, 둘 이상 충돌한 자리는 0 으로 둔다.
2. 충돌한 키들만 다음 층의 입력 `F₁` 로 보낸다. 층이 깊어질수록 키가 줄어 배열도 작아진다.
3. **질의**: 키를 층 0 부터 차례로 해시해 처음 1 을 만나는 층 `d` 에서 멈춘다. 그 위치(앞 층들의 크기 합 + 층 내 위치)가 완전 해시 값이다.
4. **최소화**: 1 비트의 누적 개수(rank) 구조를 얹어 [0, n) 로 압축한다. 기본값은 512 위치마다 64비트 카운터를 둬 크기를 1.125 배로 한다.
5. **γ 매개변수**: 배열을 키 수의 γ 배로 크게 잡으면 충돌이 줄어 만들기와 질의가 빨라지고, 구조는 커진다. γ=1 이 가장 작다.

논문의 분석으로 γ=1 일 때 층 d 의 배열 크기는 `|A₀|(1−e⁻¹)ᵈ` 로 줄어 전체 비트 수는 약 `eN`(키당 e≈2.72 비트), 일반 γ 에서는 `γ·e^(1/γ)·N` 비트다. rank 오버헤드까지 더하면 γ=1 에서 약 3.06 비트, γ=2 에서 약 3.7 비트다. 이것이 초록에서 말하는 "원소당 3.7 비트"다. 구현은 병렬 C++ 이며, 초록은 8 스레드로 10¹⁰ 개 키를 7분 미만·메모리 5GB 로 만들었다고 보고한다.

### RecSplit: 재귀 분할 후 작은 집합은 무차별 탐색

1. 키를 평균 크기 `b` 의 버킷으로 나눈다. 버킷마다 독립이라 병렬·분산 구성이 가능하다.
2. 버킷을 리프 크기 `l` 이하가 될 때까지 재귀로 쪼갠다. 한 노드에서는 해시 함수를 `0, 1, 2, …` 순으로 시도해, 키가 정해진 크기로 나뉘는 **첫 함수의 번호**를 "분할 인덱스"로 저장한다.
3. 리프에서는 크기 `l` 집합을 `[0, l)` 에 일대일로 보내는 **첫 함수의 번호**("전단사 인덱스")를 저장한다.
4. 저장하는 것은 이 번호들뿐이다. 번호는 기하분포를 따르므로 Golomb-Rice 코드로 부호화하고, 버킷의 접두합·오프셋은 Elias-Fano 로 압축한다.
5. **룩업**: 버킷을 정하고 분할 트리를 따라 리프까지 내려가며, 지나온 왼쪽 키 수를 더한 뒤 리프의 전단사 함수를 적용한다.

리프 탐색의 비용은 키 `l` 개를 `l` 칸에 겹침 없이 넣는 확률의 역수, 즉 약 `lˡ/l!` 번 시도다. `l` 이 하나 늘 때 시도 횟수는 대략 e 배가 되며 논문도 만드는 시간이 리프 크기 1 증가에 약 e 배가 된다고 확인한다. 공간은 리프가 커질수록 하한 1.44 비트에 다가간다.

### 직접 실행해 확인

두 알고리즘의 핵심만 직접 구현해(2만 개 키) 확인했다. 아래는 장난감 구현의 결과이며 논문 수치를 대체하지 않는다.

| 항목 | 실측 | 이론 |
| --- | --- | --- |
| BBHash γ=1, 비트/키(rank 제외) | 2.715 | e = 2.718 |
| BBHash γ=2 | 3.287 | 2·e^½ = 3.297 |
| BBHash γ=5 | 6.116 | 5·e^⅕ = 6.107 |
| γ=1 에 rank(×1.125) 포함 | 3.06 | 논문 표 3.07 |
| BBHash γ=2 의 전수 검사 | 2만 키가 서로 다른 값 2만 개, 0~19999 | 최소 완전 해시 |
| RecSplit 리프 l=4 평균 시도 | 10.6 | 4⁴/4! = 10.7 |
| l=8 | 399 | 8⁸/8! = 416 |
| l=9 | 1139 | 9⁹/9! = 1068 |

리프 번호만 이상적으로 부호화했을 때의 비트/키는 `log₂(e·lˡ/l!)/l` 로 l=8 에서 약 1.27 이다. 논문 표의 l=8,b=100 이 1.79 비트인 차이는 분할 인덱스·버킷 접두합·오프셋 등 나머지 구성 요소가 차지한다.

### 논문의 실측 (키 100만 개, 표 1 발췌)

| 구조 | 비트/키 | 만들기(ns/키) | 룩업(ns/키) |
| --- | --- | --- | --- |
| BBHash γ=1 | 3.07 | 96 | 33 |
| RecSplit l=5, b=5 | 2.95 | 139 | 47 |
| RecSplit l=8, b=100 | 1.79 | 1,027 | 67 |
| RecSplit l=12, b=9 | 2.23 | 7,245 | 39 |
| CHD λ=5 | 2.07 | 1,627 | 91 |
| RecSplit l=16, b=2000 | 1.56 | 1,733,801 | 87 |

키 10억 개(표 2)에서는 구조가 캐시에 안 들어가 룩업이 한 자릿수 배로 느려진다(BBHash 172ns, RecSplit l=8,b=100 은 227ns). 비트/키는 키 수와 거의 무관하다고 논문이 밝힌다. 시간은 논문의 측정 환경 값이므로 하드웨어에 따라 다르다.

## 비교

| 쟁점 | BBHash | RecSplit |
| --- | --- | --- |
| 공간(논문 기준) | γ=1 에서 약 3.07 비트. 작게 만들수록 느려짐 | 1.56~2.95 비트까지 선택. 2 비트 장벽을 실무적으로 처음 깼다고 주장 |
| 만드는 시간 | 매우 빠름 | 리프를 키울수록 지수적으로 느려짐(l=16 은 키당 약 1.7ms) |
| 룩업 | 공간이 클 때 빠름(33ns) | 리프를 키우면 더 빠르고 작아짐(논문 서술), 트리 순회 비용 있음 |
| 만들 때 RAM | 최종 구조 크기만큼의 RAM 이 필요하다고 논문이 지적 | 버킷별 독립 처리라 디스크·분산 구성 가능 |
| 병렬화 | 키를 스레드에 나눠 같은 배열에 쓰기(원자 연산), 캐시 미스가 한계 | 버킷 단위 병렬 |
| 조정 손잡이 | γ(층 크기) | 리프 크기 l, 버킷 크기 b |

## 언제 쓰나

- **BBHash**: 키가 수십억이고 구조가 비교적 커도 되며 만드는 시간이 짧아야 할 때. 다중 스레드 구성이 쉽다.
- **RecSplit**: 구조가 메모리·디스크에 오래 상주하고 키당 비트 하나가 곧 비용이어서, 오프라인으로 오래 만들 수 있을 때. 대규모 키는 버킷 단위 분산 구성.
- 룩업 속도가 최우선이면 [PTHash](/develop-wiki/knowledge/algorithms/perfect-hashing-pthash/) 같은 다른 계열과도 같은 지표로 비교해야 한다. 이 노트는 PTHash 와의 수치 비교를 확인하지 못했다.

## 주의·비용

- MPHF 는 **집합에 없는 키의 결과를 보증하지 않는다.** 소속 여부는 별도 지문이나 키 저장으로 확인한다. [XOR 필터](/develop-wiki/knowledge/algorithms/quotient-xor-filter/) 등과 조합한다.
- 키 집합이 바뀌면 다시 만든다. 정적 구조다.
- 해시 함수가 약하면 최악 입력에서 층·분할이 불균형해진다. [해시 함수와 HashDoS](/develop-wiki/knowledge/algorithms/hash-functions-hashdos/) 참고.
- RecSplit 의 리프를 키우는 선택은 구성 시간을 지수적으로 늘린다. 매개변수를 한 단계씩 올려가며 시간을 측정한다.
- BBHash 는 γ 를 크게 잡으면 구성 중 메모리가 구조 크기의 두 배까지 늘 수 있다는 논문의 분석(γ ≤ 약 1.44 이면 구조 크기만큼)이 있다.
- 두 구조의 코드·수치는 후속 연구에서 크게 개선됐을 수 있다. 최신 구현의 벤치마크를 확인한다.

> 출처 확인 범위: RecSplit 논문(arXiv 1910.06416)은 본문 PDF 를 직접 풀어 4~9절(구성, 표 1·2, 결론)을 읽었다. BBHash 논문(arXiv 1702.03154)은 초록과 2절 알고리즘·분석·구현 절 앞부분을 읽었다. 미확인: BBHash 의 실험 절 수치, Golomb-Rice 코드 세부 구현, 후속 개량(예: SIMD RecSplit, 이후 MPHF 비교 논문). 표의 장난감 구현 값은 직접 실행한 결과다.
