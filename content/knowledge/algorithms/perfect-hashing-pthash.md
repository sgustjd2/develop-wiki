## 문제

변하지 않는 키 집합 S(n 개)에 0~n−1 의 번호를 하나씩 붙이고 싶다. 빈 칸 없이 꽉 차게(minimal) 충돌 없이(perfect) 보내는 함수 `f` 가 **최소 완전 해시 함수(MPHF)** 다. 검색엔진의 단어 번호, 데이터베이스의 정적 키 인덱스처럼 한 번 만들고 여러 번 읽는 곳에 쓰인다.

일반 [해시 테이블](/develop-wiki/knowledge/algorithms/hash-table/)로 같은 번호를 매기면 키 자체를 저장해야 하고 번호도 Θ(n log n) 비트가 든다. MPHF 는 **S 에 없는 키에서 `f` 가 무엇을 내놓든 상관하지 않는 대신** 키를 저장하지 않는다. 그 덕분에 공간 하한이 키당 log₂e ≈ 1.44 비트까지 내려가며, 입력의 크기나 종류와 무관하다(PTHash 논문 설명).

핵심은 세 지표의 균형이다: **만드는 시간**, **룩업 시간**, **표현 공간**.

## 해법 계열 (논문이 정리한 네 갈래)

| 계열 | 아이디어 | 특징 |
| --- | --- | --- |
| 해시 & 변위 (FCH, CHD) | 키를 버킷으로 나누고 버킷마다 변위 값을 골라 충돌 없이 배치 | 룩업이 빠르다. FCH 는 만드는 시간이 길고 공간이 큼 |
| 선형 시스템 | 키마다 방정식을 세워 풂. 하이퍼그래프 박리로 선형 시간에 풂 | [XOR 필터](/develop-wiki/knowledge/algorithms/quotient-xor-filter/)와 같은 박리 기법 계열 |
| 지문 (BBHash) | 충돌 없는 키부터 비트맵에 표시하고 충돌 키는 다음 층으로 | 만들기·읽기 빠름, 파라미터 γ 가 클수록 공간 증가 |
| 재귀 분할 (RecSplit) | 작은 집합은 브루트포스로 찾고 나머지는 분할 | 매우 작은 공간. 층마다 메모리 접근이 늘어 룩업이 느림 |

## PTHash 의 구조

PTHash(Pibiri·Trani, SIGIR 2021)는 1992 년 FCH 의 세 단계 틀(매핑·정렬·탐색)을 되살리되, **탐색 단계를 갈아엎어** 출력이 잘 압축되게 만들었다.

1. **매핑**: 키를 비균등 버킷 `m ≈ c·n / log₂n` 개에 넣는다. 키의 60% 가 앞쪽 30% 버킷에 몰리도록 한다. `c` 는 공간과 만드는 시간을 맞바꾸는 파라미터다.
2. **정렬**: 버킷을 크기 내림차순으로 처리한다. 논문은 이 순서가 탐색을 빠르게 하고, 적재율이 높아지는 뒤쪽에서는 작은 버킷만 남아 파일럿 값을 작게 유지한다고 설명한다.
3. **탐색**: 버킷마다 정수 **파일럿** `k` 를 0, 1, 2, … 순서로 시도한다. 키 `x` 의 위치는 `(h(x) xor h(k)) mod n` 이고, 버킷의 모든 위치가 비어 있고 서로 겹치지 않는 첫 `k` 가 그 버킷의 파일럿이다. 파일럿 표 `P[0..m−1]` 이 함수의 전부다.

**룩업**은 버킷 번호를 계산하고 `P[i]` 를 한 번 읽어 위치를 계산하는 것이 전부다.

```python
def lookup(key, pilots, P):
    n, m, p1, p2, s1, s2 = P
    a = mix(key ^ s1)
    b = a % p2 if (a % n) < p1 else p2 + (a % (m - p2))   # 비균등 버킷
    return (mix(key ^ s2) ^ mix(pilots[b] ^ s2 ^ 0xABCDEF)) % n
```

FCH 는 변위를 무작위로 골라 `P` 가 압축되지 않았다. PTHash 는 파일럿을 작은 값부터 순서대로 시도하므로 값이 **작고 한쪽으로 치우친 분포**가 되어 잘 압축된다. 파일럿이 `v` 일 확률은 기하분포를 따르고 기댓값은 `(1 / (1−α)^|B|) − 1`(α = 그 시점의 적재율, |B| = 버킷 크기)로 모형화되며 논문 실험에서 측정값과 거의 일치한다. 앞쪽 버킷은 적재율이 낮을 때 처리돼 파일럿이 더 작아서, `P` 의 앞부분과 뒷부분을 서로 다른 인코딩으로 저장할 수 있다. 인코딩 방식으로 사전 인코딩·Elias–Fano·SDC 등을 쓰며 압축이 클수록 룩업이 느려지는 교환이 있다.

탐색 시간은 특히 적재율이 1 에 가까운 마지막 버킷에서 길어진다. 논문은 `n` 대신 `n′ = n/α` 칸에서 찾고 남는 빈 자리를 `free` 배열로 접어 넣는 방식으로 최대 적재율을 제한해 이를 줄인다.

## 직접 구현해 확인한 것

α=1 의 단순화 구현(Python, 키 10만 개, 64 비트 무작위 정수)을 실행했다. 모든 설정에서 출력이 `0..n−1` 의 순열(최소 완전)임을 확인했다.

| c | 버킷 수 | 탐색 시간 | FCH 식 고정폭 | 파일럿 0차 엔트로피 | 사전 인코딩 |
| --- | --- | --- | --- | --- | --- |
| 3.5 | 21,073 | 2.6 s | 3.79 bit/key | 1.86 | 2.60 |
| 5.0 | 30,103 | 1.0 s | 5.42 | 2.04 | 3.13 |
| 7.0 | 42,145 | 0.7 s | 7.59 | 2.25 | 4.32 |

- `c` 를 키우면 **만드는 시간은 줄고 공간은 늘어난다**(논문이 말한 교환과 같은 방향).
- 같은 `c` 에서 파일럿 표를 고정폭 대신 사전 인코딩으로 저장하면 공간이 31~43% 줄었다.
- 0차 엔트로피 열은 하한 추정일 뿐 실제 인코딩 크기가 아니다. 논문도 파일럿 엔트로피(n=10⁶, c=3.5 에서 10.32 비트/파일럿)와 별개로 인코딩 방식을 다룬다.
- 이 구현은 n=10⁵ 의 순수 Python 이라 **절대 수치(시간·bit/key)는 논문의 C++ 구현과 비교할 수 없다.** 논문은 1억 개 64 비트 키에서 FCH(c=3)가 1시간 10분 걸리는 같은 공간(3.0 bits/key)을 PTHash 가 c=5.6 으로 70초에 만든다고 보고한다(약 60 배).

## MPHF 위에 만드는 것

MPHF 는 키의 번호만 준다. 다음을 얹어 쓴다.

- **정적 사전(키 → 값)**: 값을 `f(key)` 위치의 배열에 둔다. 값이 MPHF 보다 훨씬 크면 MPHF 가 2 비트냐 3 비트냐는 중요하지 않고 **룩업 속도와 만들 수 있느냐**가 더 중요하다는 것이 논문의 입장이다.
- **S 에 없는 키 걸러내기**: `f` 는 S 밖의 키에도 어떤 번호를 돌려주므로, 소속 확인이 필요하면 키의 지문을 같이 저장해 비교한다. 이것이 [XOR·퓨즈 필터](/develop-wiki/knowledge/algorithms/ribbon-binary-fuse-filters/)가 해결하는 문제(지문만 저장하고 소속을 근사 판정)와 맞닿는다.
- Bloom 필터 변형, 압축 인덱스 등에 MPHF 를 부품으로 쓰는 사례를 논문이 열거한다.

## 언제 쓰나

- 키 집합이 **고정**이고 한 번 만든 뒤 많이 읽는 경우(사전 번호 매기기, 읽기 전용 키-값 저장소, 인덱스 압축).
- 키 저장 공간을 아끼고 싶은데 룩업이 메모리 접근 한두 번으로 끝나야 할 때.
- 구현은 PTHash 저자의 C++ 라이브러리(`jermp/pthash`)가 논문에서 소개돼 있다. 직접 구현보다 먼저 확인한다.

## 주의 (비용)

- **정적**이다. 키를 추가·삭제하면 다시 만들어야 한다. 동적 집합에는 [해시 테이블](/develop-wiki/knowledge/algorithms/hash-table/)이나 쿼션트 필터류를 쓴다.
- **S 밖의 키는 검증 불가**다. 조회 키가 S 에 있다는 보장이 없으면 지문 등으로 확인 단계를 둔다.
- **만드는 시간**이 룩업보다 훨씬 길다. 논문 이론 결과로 탐색 시간은 `O(n^(1+Θ(1/c)))` 라, `c` 를 줄여 공간을 아낄수록 급격히 늘어난다(증명은 논문에서 생략). 키 수가 큰 경우 적재율을 1 미만으로 제한하는 옵션을 쓴다.
- 해시 함수 선택에 따라 시드 재시도가 필요할 수 있고, 키 분포가 적대적이면 [해시 함수와 HashDoS](/develop-wiki/knowledge/algorithms/hash-functions-hashdos/)의 논점이 그대로 적용된다.
- 이 노트는 PTHash 논문(arXiv 2104.10402)만 읽었다. RecSplit·BBHash 등 다른 계열의 수치 비교와 이후 후속 연구는 확인하지 않았다.
