> 출처 메모: Li·Mourikis, "Vision-aided Inertial Navigation with Rolling-Shutter Cameras"(IJRR 2014, 33(11)) 의 저자 공개본 PDF(UC Riverside 연구실 사이트, 이 환경에서는 웹 아카이브 사본으로 내려받음)를 텍스트로 추출해 3·4·5장과 부록 I 을 직접 읽었다(2026-11-19). 아래 식 번호와 수치는 그 공개본 기준이다. 최종 출판본과의 차이는 대조하지 않았다. 같은 저자의 ICRA 2013 롤링 셔터 논문(등속 모델, 본문에서 "Li et al. 2013")은 내려받지 못해 읽지 않았다.

## 문제

글로벌 셔터는 모든 화소를 한순간에 찍는다. 저가 CMOS 카메라(스마트폰 대부분)는 **롤링 셔터**다. 행을 위에서 아래로 차례로 읽어 한 장을 읽는 데 판독 시간(readout time) `t_r` 이 걸린다. 카메라가 움직이면 행마다 다른 자세에서 찍힌 셈이 된다.

- 논문의 Nexus 4 데이터는 `t_r = 43.3 ms`, 11 Hz 다. 프레임 간격(약 91 ms)의 절반 가까이를 판독에 쓴다.
- 이를 글로벌 셔터로 가정하고 처리하면 논문 시뮬레이션에서 위치 RMSE 가 5.4 m 로, 롤링 셔터 모델(0.43~0.47 m)보다 한 자릿수 크다.
- "정확한" 해법은 행마다 자세를 상태에 넣는 것이지만 행이 수백 개라 실시간으로 불가능하다.

## 행별 시간 모델

이미지 행 수가 `N` 이고, 판독 구간의 **중간** 시각이 `t_o` 일 때 `n` 번째 행의 촬영 시각(논문 식 1):

```
t_n = t_o + n · t_r / N,    n ∈ [−N/2, N/2]
```

- 특징점의 행 좌표 `z_r` 에서 `n = z_r − N/2` 로 행 번호를 얻는다. 측정값 자체가 촬영 시각을 정한다.
- 논문은 이미지 타임스탬프가 판독 중간을 가리킨다고 **규약**으로 정하고, 카메라-IMU 시간 오프셋 `t_d` 를 더해 실제 중간 시각을 `t + t_d` 로 둔다([EKF 시간 오프셋 추정](/develop-wiki/knowledge/robotics/ekf-camera-imu-time-offset-estimation/)). 타임스탬프가 판독 시작을 가리키는 장비라면 `t_r/2` 차이가 `t_d` 에 흡수된다.

## 기존 근사: 궤적을 낮은 차원으로

| 방식 | 판독 구간의 움직임 표현 | 논문이 지적한 약점 |
| --- | --- | --- |
| 특징 좌표 보정 후 GS 처리 | 등속 가정으로 좌표를 "펴기" | 3D 점과 움직임을 완전히 알아야 정확, 근사 불가피 |
| 등속 모델 | 판독 중 선속도·각속도 일정 | 가속이 크면 모델 오차. 속도 상태 추가 필요 |
| B-spline·시간 기저 함수 | 궤적을 스플라인으로 | 빠른 움직임에서 매듭(knot)을 촘촘히 → 상태 수 증가 |

논문은 손에 든 폰으로 걸을 때 1 초 구간의 IMU 를 보여 준다. 판독 구간마다 최적 상수 근사의 각속도 오차가 최대 81.8 °/s, 선형 근사도 20.9 °/s 였다. 가속도의 최적 선형 근사 오차는 최대 1.03 m/s² 로 가속도계 잡음보다 한 자릿수 크다. 그래서 4차 B-spline 으로 맞추려면 약 15 ms 마다, 즉 이미지당 3 개 정도의 매듭이 필요하다고 추정한다.

## 해법: 잔차는 정확히, 선형화만 근사

선형화 기반 추정기(EKF, 반복 최적화)는 두 가지가 필요하다. 잔차 계산(추정값 사용)과 잔차-오차 관계의 선형식(오차 사용)이다. 논문은 둘을 다르게 다룬다.

1. **잔차**: 상태에는 판독 중간 `t_o` 의 IMU 상태만 둔다. 행 `n` 의 자세 `p̂(t_n)`, `q̂(t_n)` 은 판독 구간의 IMU 측정을 적분해 구한다. 궤적 모양에 가정이 없고, IMU 대역폭 안의 움직임은 다 반영된다.
2. **선형화**: 행 `n` 의 오차를 `t_o` 의 오차와 그 미분으로 테일러 전개하고 낮은 차수에서 자른다(식 7·8). 위치는 `l_p` 차, 자세는 `l_θ` 차.
   - `l_p = 1, l_θ = 0` 이면 `r ≈ H_θ θ̃(t_o) + H_p p̃(t_o) + (n t_r / N) H_p ṽ(t_o) + H_a x̃_a + n` (식 16).
   - `l_p = l_θ = 0` 이면 속도 항도 빠지고 GS 와 같은 상태로 처리한다.
3. **자른 항의 상한**: 오차의 크기는 추정기가 이미 알고 있으니(필터 공분산, 센서 사양) 버린 항이 잔차에 주는 영향을 미리 계산할 수 있다.
   - 위치(`l_p = 1`): `δ̄_p = (√3/8) H_pu t_r² ε_a` (식 13)
   - 자세(`l_θ = 0`): `δ̄_θ = (√3/2) H_θu t_r ε_ω` (식 15)
   - 위치(`l_p = 0`): `δ̄'_p = √3 H_pu (t_r/2) ε_v` (식 17에 `n = N/2`)
   - `H_pu`, `H_θu` 는 투영 야코비안 노름의 상한이다. 부록 I 에서 초점거리 `a_u`, 화각 `F`, 깊이 `z` 로 `H_pu = (a_u/z)·√(1+tan²(F/2))`, `H_θu = a_u·(1+tan²(F/2))` 이다.

```ts
// 논문 3장의 상한 계산 (부록 I 의 야코비안 상한 사용). 단위: px
const bounds = (au: number, fovRad: number, depth: number, tr: number,
                epsA: number, epsW: number, epsV: number) => {
  const s = 1 + Math.tan(fovRad / 2) ** 2;
  const Hp = (au / depth) * Math.sqrt(s), Hth = au * s;
  return {
    pos_lp1: (Math.sqrt(3) / 8) * Hp * tr * tr * epsA,
    rot_l0: (Math.sqrt(3) / 2) * Hth * tr * epsW,
    pos_lp0: Math.sqrt(3) * Hp * (tr / 2) * epsV,
  };
};
// bounds(500, Math.PI/3, 2, 0.0433, 1, Math.PI/180, 0.2)
```

### 직접 확인: 논문 예시 수치

위 함수에 논문 값(`a_u = 500 px`, 화각 60°, 깊이 2 m, `t_r = 43.3 ms`, `ε_a = 1 m/s²`, `ε_ω = 1 °/s`, `ε_v = 0.2 m/s`)을 넣어 Node.js 로 계산했다.

| 항 | 논문 | 직접 계산 |
| --- | --- | --- |
| `δ̄_p` (`l_p = 1`) | 0.12 px | 0.117 px |
| `δ̄_θ` (`l_θ = 0`) | 0.44 px | 0.436 px |
| `δ̄'_p` (`l_p = 0`) | 2.2 px | 2.165 px |

`l_p = 1, l_θ = 0` 이면 버린 항의 합이 0.56 px 이하로, 논문이 쓴 영상 잡음 표준편차 0.75 px 보다 작다. `l_p = 0` 은 상한이 2.2 px 로 크지만, 논문은 실험에서 성능 손실이 작아 이 상한이 보수적이라고 판단했다. 이 계산은 공식 대입 확인이지 추정기 재현이 아니다.

## 논문이 보고한 것

시뮬레이션은 Nexus 4 실제 데이터(4.23 분, 약 227 m 보행)로 만든 궤적, 50 회 몬테카를로, 하이브리드 EKF(MSCKF + EKF-SLAM 특징) 위에서 비교했다(표 II).

| 방법 | 위치 RMSE (m) | 자세 RMSE (°) | NEES (기대 9) | 갱신당 시간 (ms) |
| --- | --- | --- | --- | --- |
| 글로벌 셔터 가정 | 5.403 | 15.12 | 571.2 | 0.85 |
| 등속 모델(Li et al. 2013) | 0.806 | 1.34 | 19.78 | 2.17 |
| 제안 `l_p=0, l_θ=0` | 0.471 | 0.735 | 11.05 | 0.87 |
| 제안 `l_p=1, l_θ=0` | 0.447 | 0.693 | 10.64 | 1.49 |
| 제안 `l_p=1, l_θ=1` | 0.427 | 0.695 | 10.44 | 2.24 |

- 차수를 올리면 정확도는 10% 이내로 조금 좋아지고 비용은 2.5 배 이상 커졌다. 실제 실험은 `l_p = l_θ = 0` 을 썼다.
- 실차 약 11 km(Galaxy SIII): 최대 위치 오차 약 63 m, 등속 모델은 123 m.
- 로봇 약 720 m(Nexus 4): 최종 오차가 이동 거리의 0.73%.
- 실내 보행 약 523 m, 폰에서 실시간: 최종 오차 약 0.16%, EKF 갱신당 평균 13.6 ms.
- 실험에서 `t_r` 은 기기별 고정값(표 III: Nexus 4 43.3 ms, Galaxy SIII 15.9 ms, Galaxy SII 32.0 ms)으로 주어진다. 공개본에는 이 값을 어떻게 얻었는지 적혀 있지 않고, `t_r` 을 온라인 추정하지 않는다.

## 언제 쓰나

- 스마트폰, 저가 USB·MIPI 카메라처럼 롤링 셔터만 있는 장비로 VIO 를 할 때.
- 손에 든 기기, 소형 드론처럼 판독 시간 안에 각속도가 크게 바뀌는 경우. 등속 모델이 깨지는 구간이다.
- 이미 슬라이딩 윈도 EKF(MSCKF 계열)를 쓰고 있고 상태 수를 늘리고 싶지 않을 때. `l = 0` 이면 추가 상태 없이 행별 자세를 IMU 적분으로만 구한다.

## 주의/비용

- **판독 시간 `t_r` 이 맞아야 한다.** 이 모델은 `t_r` 을 입력으로 받는다. 센서 데이터시트나 별도 보정으로 얻어야 하고, 틀리면 행별 시각이 일괄적으로 틀린다. 해상도·프레임률 모드를 바꾸면 `t_r` 도 바뀔 수 있다.
- **IMU 대역폭 밖의 움직임**(진동, 충격)은 IMU 적분으로도 표현되지 않는다.
- 상한 계산은 **보수적 가정**(초점거리, 화각, 최소 깊이, 오차 상한)에 의존한다. 가까운 물체(작은 `z`)는 `H_pu` 를 키운다.
- 행별로 IMU 를 적분하는 비용이 추가된다. 논문은 행렬 연산에 비해 작다고 본다.
- 시뮬레이션의 정답 궤적은 제안 방법 자체의 추정 결과에서 만들었다. 다른 방법과의 비교가 이 궤적 생성 방식에 영향을 받는지는 논문이 따로 분석하지 않았다.
- 판독 시간과 시간 오프셋 `t_d`, 타임스탬프 규약(시작·중간·끝)이 서로 얽힌다. 규약을 바꾸면 `t_d` 의 의미가 바뀐다.

## 검증 범위

- 직접 읽음: 저자 공개본의 1~5장, 부록 I·II, 표 II·III.
- 읽지 않음: 최종 출판본(차이 미대조), ICRA 2013 등속 모델 논문, 비교 대상인 Hedborg·Lovegrove·Oth 논문.
- 공개 구현 VINS-Mono 의 `TR/ROW*row` 항([시간 오프셋 노트](/develop-wiki/knowledge/robotics/camera-imu-time-offset-online-calibration/))이 이 모델과 같은 시간 규약인지는 확인하지 않았다.
