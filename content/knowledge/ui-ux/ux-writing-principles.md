## 문제

- 같은 동작이 화면마다 "저장", "확인", "완료", "적용"으로 바뀐다.
- 버튼이 "확인"뿐이라 누르면 무슨 일이 일어나는지 모른다.
- "회원님의 소중한 정보를 안전하게 보호하기 위하여…"처럼 앞부분에 핵심이 없다.
- 개발 용어("세션 토큰 만료", "동기화 충돌 409")가 그대로 노출된다.

## 해법

### 1. 명확성

- **핵심 단어를 앞에.** 사람은 화면을 읽기보다 훑는다. "총 결제 금액"이 "이것은 총 결제 금액입니다"보다 낫다.
- **한 문장에 한 생각, 필요한 만큼만.** 적게 시작하고 리서치에서 필요가 확인되면 늘린다.
- **사용자의 말로.** 내부 조직명·기술 용어 대신 사용자가 검색할 때 쓰는 단어.
- **설명이 길어지면 UI 를 고친다.** 문구로 복잡한 인터페이스를 구할 수 없다.

### 2. 행동 중심 레이블

Apple HIG 는 버튼·링크 레이블에 거의 항상 동사를 쓰고, 재치보다 명확성을 우선하라고 한다.

| 나쁜 예 | 고친 예 | 이유 |
| --- | --- | --- |
| 확인 | 주문하기 / 저장 | 결과를 말한다 |
| 예 / 아니요 | 파일 삭제 / 취소 | 질문을 다시 읽지 않아도 된다 |
| 여기를 클릭하세요 | 환불 정책 보기 | 링크만 들어도 목적을 안다(WCAG 2.4.4) |
| 제출 | 신청서 제출 | 대상 명시 |
| 가자! 🚀 | 시작하기 | 재치보다 명확성 |

- 여러 단계 흐름은 시작("시작하기") → 진행("다음"/“계속”) → 끝("완료")을 일관되게.
- 보이는 레이블이 접근 가능한 이름에 들어가야 음성 명령으로 누를 수 있다(WCAG 2.5.3). → [접근 가능한 이름](/develop-wiki/knowledge/ui-ux/screen-reader-accessible-name/)

### 3. 일관성: 용어집과 패턴

- 제품 **용어집**을 만든다: 한 개념 = 한 단어("삭제" vs "제거", "계정" vs "프로필").
- **화자 시점**을 정한다: 서비스가 말할 때 "~하세요"(합쇼체·해요체 중 하나), 사용자가 말하는 버튼은 "~하기" 또는 명사형.
- 대문자·띄어쓰기·문장부호 규칙을 컴포넌트별로 정한다(영문은 sentence case/title case 중 하나).
- 소유격("내 ~", "회원님의 ~")은 아껴 쓴다. Apple HIG 는 "우리(we)"도 누구를 말하는지 모호하니 피하라고 한다: "불러오는 데 문제가 있어요"보다 "콘텐츠를 불러올 수 없음".

### 4. 톤

- 목소리(voice)는 제품 전체에 고정, 톤(tone)은 상황에 맞춘다. 결제 오류는 담백하게, 목표 달성은 가볍게.
- 오류에는 농담·과한 사과를 쓰지 않는다. 사과는 서비스 잘못일 때만. → [에러 메시지](/develop-wiki/knowledge/ui-ux/error-messages/)
- 기기에 맞는 동사: 터치 기기에서 "클릭" 대신 "탭"·"누르기".

### 5. 한국어 UI 에 적용

- 종결 어미를 한 가지로: 안내문은 "~하세요"/“~해요” 중 하나, 버튼은 "저장"/“저장하기” 중 하나로 통일.
- 한자어·번역투 줄이기: "~에 대하여", "~를 진행하다", "~되어지다" → "~를", "~하다".
- 외래어는 국립국어원 표기(“메시지”, “콘텐츠”, “로그인”)와 제품 용어집을 맞춘다.
- 번역을 전제로 쓴다: 문장 조각을 이어 붙이지 않는다. → [국제화 UX](/develop-wiki/knowledge/ui-ux/i18n-ux/)

## 언제 쓰나

- 버튼·라벨·오류·빈 상태·확인 대화상자·알림 등 모든 마이크로카피. 디자인 시안 단계에서 실제 문구로 작업한다("Lorem ipsum" 금지).
- 디자인 시스템에 문구 패턴(오류, 빈 상태, 확인)을 컴포넌트와 함께 정의할 때.

## 체크리스트

- 모든 버튼이 결과를 말하는 동사(구)다.
- 용어집과 화면 문구가 일치한다.
- 핵심 문구를 소리 내어 읽었을 때 자연스럽다.
- 문구만 따로 뽑아 읽어도(낭독기 링크 목록처럼) 뜻이 통한다.
- 실제 사용자와 문구를 테스트했다(첫 클릭 테스트, 이해도 질문).

## 흔한 실수·주의

- **문구를 개발 마지막에 채움.** 레이아웃이 짧은 영어·한국어 기준으로 고정돼 번역·변경을 못 견딘다.
- **브랜드 개성 과잉.** 반복해서 보는 문구의 재치는 금방 피로해진다.
- **약어·축약.** 공간을 아끼려다 이해를 잃고, 다른 언어로 옮길 수 없다.
- 규칙은 출발점이다. 사용성 테스트·분석(오류 빈도, 이탈 지점)으로 문구를 검증한다.
