## 문제

정적 집합(한 번 만들고 읽기만 하는 집합)의 확률적 소속 검사에서 이론 하한은 오탐률 ε 일 때 원소당 `log₂(1/ε)` 비트다. 블룸 필터는 이보다 최소 44% 더 쓰고, [XOR 필터](/develop-wiki/knowledge/algorithms/quotient-xor-filter/)는 약 23% 더 쓴다. LSM 트리의 가장 큰 층처럼 **오래 살고 메모리에 상주하는 필터**에서는 이 몇 십 %가 곧 비용이다. 두 논문이 이 오버헤드를 더 줄인다.

둘 다 XOR 필터와 뼈대가 같다. 원소의 지문(fingerprint)을 만들고, 조회 때 해시로 고른 칸 몇 개의 **XOR 가 지문과 같은지** 본다. 달라지는 것은 "칸을 어떻게 고르고, 그 방정식을 어떻게 푸느냐"다.

## 이진 퓨즈 필터 (Graf·Lemire, 2022)

XOR 필터는 배열을 3등분해 구간마다 칸 하나씩 고른다. 퓨즈 필터는 배열을 **수백 개의 작은 구간(segment)** 으로 나누고, 키마다 시작 구간을 하나 정한 뒤 **연속한 세 구간에서 칸 하나씩** 고른다. 구간 길이를 2의 거듭제곱으로 맞추면(binary) 구간 안의 위치를 비트 마스크로 계산할 수 있다.

- 키가 흩어지는 범위가 좁아져 껍질 벗기기(peeling)가 구간 순서대로 지역적으로 진행된다. 캐시에 잘 맞아 구성도 빨라진다(논문은 XOR 필터 대비 구성이 2배 이상 빠를 수 있다고 보고).
- 같은 성공 확률을 얻는 데 필요한 배열이 작아진다. 큰 집합에서 3-wise 는 약 `1.125n`, 해시를 4개 쓰는 4-wise 는 약 `1.075n` 이다. 하한 대비 오버헤드는 각각 약 13%, 약 8%(XOR 필터는 23%)다.
- 조회는 XOR 필터와 같고, 4-wise 는 칸이 하나 늘어 논문 기준 질의가 약 30% 느려진다.
- 크기는 논문 Table 1 의 공식을 쓴다. 3-wise: 배열 `⌊n × (0.875 + 0.25 × max(1, ln(10⁶)/ln n))⌋` 이상, 구간 길이 `2^⌊ln n / ln 3.33 + 2.25⌋`. 배열은 구간 길이의 배수로 올림하고 구간은 최소 3개를 둔다. 작은 n 에서는 여유를 더 둔다.

### 직접 돌려 본 결과

위 공식으로 3-wise, 8비트 지문을 구현해 키 수를 바꿔 가며 시드 10개를 시도했다(구성 실패 시 시드를 바꿔 재시도).

| n | 구간 길이 | 배열 크기 | 키당 비트 | 시드 10개 중 성공 | 거짓 음성 | 오탐률(이론 0.391%) |
| --- | --- | --- | --- | --- | --- | --- |
| 10,000 | 512 | 1.280 n | 10.24 | 10 | 0 | 0.406% |
| 100,000 | 2048 | 1.188 n | 9.50 | 10 | 0 | 0.382% |
| 약 100만 | 8192 | 1.131 n | 9.04 | 10 | 0 | 0.416% |

- 같은 8비트 지문에서 XOR 필터는 `1.23n + 32` 칸이라 원소당 약 9.84 비트다. n 이 클수록 퓨즈 쪽 배열이 1.125n 에 가까워지는 것이 보인다. 100만 개에서 키당 9.04 비트로, 하한 8비트 대비 약 13%다.
- n 이 작으면(1만) 여유 계수가 커져서 이득이 줄어든다. 논문도 집합이 클 때(수만 개 이상) 퓨즈가 유리하다고 말한다.
- 이 값은 내 구현과 해시 함수 기준이며 속도는 측정하지 않았다.

## Ribbon 필터 (Dillinger·Walzer, 2021)

Ribbon 은 방정식을 푸는 방식을 바꾼다. 각 키는 배열의 시작 위치 `s` 와 `w` 비트 계수 벡터 `c` 를 가지며, 그 키의 방정식은 **`Z[s..s+w)` 안의 칸들 중 `c` 의 1 비트에 해당하는 것들의 XOR = 지문** 이다. 방정식 행렬을 시작 위치로 정렬하면 0 이 아닌 값이 대각선을 따라 폭 `w` 의 **띠(ribbon)** 안에만 있어서, 가우스 소거를 해도 띠 밖으로 채워지지 않는다.

- 삽입은 해시 테이블처럼 진행한다(논문 표현으로 "on-the-fly banding"). 시작 위치의 행이 비었으면 방정식을 놓고, 차 있으면 두 방정식을 XOR 해서 맨 앞 1 비트를 지운 뒤 다음 1 비트 위치로 옮겨 계속한다. 결국 계수가 전부 0 이 되면 지문 값이 0 이면 중복 방정식(문제 없음), 0 이 아니면 모순이라 시드를 바꿔 다시 한다.
- 모든 키를 넣은 뒤 **뒤쪽 칸부터 역대입**해 `Z` 를 채운다.
- 조회는 `s` 부터 `w` 칸 안에서 `c` 가 가리키는 칸들의 XOR 를 지문과 비교한다. 칸들이 연속이라 캐시 친화적이다.
- `w` 가 클수록 더 촘촘한(`m` 이 `n` 에 가까운) 배열에서도 풀린다. 논문은 `w = O(log n / ε)` 이면 `m = (1+ε)n` 에서 높은 확률로 풀린다고 증명한다. 시작 위치 분포의 양 끝을 부풀리는 **smash**, 지문 없이 동차 방정식을 푸는 **Homogeneous Ribbon**(구성이 실패하지 않는 대신 오탐률이 이론값보다 높아질 수 있고 작은 n 에서 변동이 큼) 같은 변형도 제안한다. 논문은 일부 설정에서 공간 오버헤드 10% 미만, 실험적 변형에서는 1% 미만까지 보고하며, 그 대가로 CPU 시간이 더 든다고 한다.
- RocksDB 에 이 필터 옵션이 들어갔다고 논문 각주가 밝힌다(6.15.0, 2020년 11월).

```ts
// 표준 Ribbon 삽입(밴딩). 폭 w=32, 계수 최하위 비트는 항상 1. C[i]=0 이면 빈 행
function insert(C: Uint32Array, B: Uint8Array, s: number, c: number, b: number): boolean {
  for (let i = s; ; ) {
    if (C[i] === 0) { C[i] = c; B[i] = b; return true; }  // 빈 행: 방정식 등록
    c = (c ^ C[i]) >>> 0; b ^= B[i];                      // 같은 시작 위치의 방정식과 XOR → 최하위 1 이 사라짐
    if (c === 0) return b === 0;                           // 지문까지 0 이면 중복, 아니면 모순(재시도)
    const tz = 31 - Math.clz32(c & -c); c >>>= tz; i += tz; // 다음 1 비트 위치로 이동
  }
}
```

### 직접 돌려 본 결과

표준 Ribbon(smash·homogeneous 없음)을 구현해 `r = 8` 비트 지문으로 실험했다.

**폭 w=32, n = 100,000** (시드 20개)

| 배열 크기 m | 성공한 시드 |
| --- | --- |
| 1.03 n ~ 1.10 n | 0 / 20 |
| 1.15 n | 2 / 20 |
| 1.25 n | 18 / 20 |

`m = 1.15n` 에서 성공한 필터로 측정했다. 거짓 음성 **0**, 오탐률 **0.397%**(이론 0.391%), 키당 **9.20 비트**(하한 8 비트 대비 오버헤드 15%).

**폭에 따른 성공률, n = 50,000** (시드 10개, 밴딩 단계 성공 여부)

| w | m = 1.05n | m = 1.10n | m = 1.15n |
| --- | --- | --- | --- |
| 32 | 0 / 10 | 0 / 10 | 1 / 10 |
| 64 | 5 / 10 | 9 / 10 | 10 / 10 |
| 128 | 10 / 10 | 10 / 10 | 10 / 10 |

폭을 두 배로 키울수록 같은 배열 크기에서 성공률이 뚜렷이 올라간다. 대신 조회가 훑는 범위가 넓어지고 삽입에서 XOR 할 비트열이 길어진다(비용 증가는 이 노트에서 측정하지 않았다).

## 언제 쓰나

- **LSM 트리의 큰 층**처럼 만들고 나면 바뀌지 않으며, 메모리를 오래 점유하는 필터. 필터 크기를 줄이면 캐시에 담을 수 있는 데이터가 늘어난다.
- 퓨즈: 키가 수만 개 이상이고 구현 단순함과 조회 속도를 함께 원할 때. Ribbon: 공간을 한 자릿수 %까지 줄이고 싶고, 그 대가로 구성·조회 시간이 약간 더 드는 것을 받아들일 때. 논문 초록은 오탐률이 큰 영역(`ε ≥ 2⁻⁷`)에서 Ribbon 이 특히 경쟁력 있는 속도를 낸다고 말한다.
- 필터의 앞단/뒷단이 비싼 확인(디스크 읽기)을 하는 경우에만 의미가 있다 → [블룸 필터](/develop-wiki/knowledge/algorithms/bloom-filter/).

## 주의 (비용)

- **정적 구조다.** 원소를 추가·삭제하려면 처음부터 다시 만든다. 삭제가 필요하면 [쿠쿠 필터](/develop-wiki/knowledge/algorithms/cuckoo-counting-bloom-filter/), 삭제·병합이 필요하면 쿼션트 필터를 본다.
- **구성이 확률적으로 실패한다.** 배열을 너무 빡빡하게 잡으면 위 표처럼 실패하므로 시드를 바꿔 재시도하는 루프가 필수다. 중복 키는 구성을 깨뜨릴 수 있으니 먼저 제거한다(XOR 필터 노트 참고).
- **구성 시 메모리**: 전체 키와 임시 배열이 한 번에 필요하다. 퓨즈는 작은 n 에서는 이득이 작다.
- 시도할 때마다 새 시드를 써야 하고, 해시 품질과 시드 비공개가 중요하다 → [해시 함수와 HashDoS](/develop-wiki/knowledge/algorithms/hash-functions-hashdos/). 공격자가 키를 고를 수 있으면 일부러 구성을 실패시키는 입력을 만들 수 있는지 검토한다.
- 위 실험의 수치는 내가 만든 학습용 구현의 것이다. 상용 구현은 SIMD, 구간 정렬 등 최적화로 속도·성공 임계가 다르다. 속도 비교는 논문의 벤치마크를 따로 본다.
- 이 노트는 두 논문의 본문 중 정의·알고리즘·표를 읽었고, Ribbon 논문의 증명 부분과 벤치마크 그림은 요약만 했다.
