> 출처 메모: van Waveren 의 "Software Virtual Textures"(id Software, 2012-02-25) 본문 3~6절과 부록 앞부분(주소 번역, 필터링, 피드백, 과구독, LOD 스냅, 저장·스트리밍·교체 정책, 결과)을 읽었다. Barrett 의 Sparse Virtual Textures 소개 페이지는 요약만 읽었고(발표 영상·슬라이드는 읽지 못함), Epic 문서 페이지는 개요 수준이라 SVT·RVT 의 장점 설명만 참고했다. Unity SVT 매뉴얼은 열었으나 본문을 확인하지 못했다. 논문은 하드웨어 스파스 텍스처 이전의 **소프트웨어 구현** 이야기라 현재 GPU 의 하드웨어 스파스 지원과 다른 부분이 있다. 아래 수치 계산은 직접 한 것이다.

## 문제

[밉맵 스트리밍](/develop-wiki/knowledge/graphics-xr/texture-streaming/)은 텍스처 객체 단위로 밉 레벨을 올리고 내린다. 지형 전체나 도시처럼 **고유한(반복되지 않는) 텍스처를 큰 면적에** 입히려면 한 텍스처 안에서도 보이는 부분만 상주시켜야 한다. 또 타일링 텍스처를 쓰던 방식은 반복이 보이고, 면마다 텍스처를 고르는 상태 변경 비용이 든다. 논문은 많은 표면이 하나의 가상 텍스처를 공유하면 드라이버·하드웨어 상태 변경도 줄어든다고 한다.

## 해법

### 구조

- **가상 텍스처**: 논문 예로 백만 페이지 규모까지 가능한, 전체가 상주하지 않는 텍스처.
- **페이지**: 정사각 블록(논문은 128×128 정도). 가장자리에 필터링용 **테두리 4텍셀** 을 포함해 128 이면 실제 페이로드는 120×120 이다.
- **물리 페이지 풀**: 완전 상주하는 작은 텍스처(보통 4096×4096, 곧 32×32=1024 페이지). 가상 페이지가 여기에 올라온다.
- **페이지 테이블**: 가상 주소를 물리 주소로 옮기는 정보. 셰이더가 텍스처 샘플 한 번 + 곱셈-덧셈으로 번역한다.

### 주소 번역

가장 직관적인 방법은 밉 사슬이 있는 페이지 테이블 텍스처를 두는 것이다. 가상 페이지당 텍셀 하나가 **물리 페이지 쪽 스케일과 바이어스** 를 담는다. 요청한 LOD 의 페이지가 아직 올라오지 않았으면 그 텍셀은 **더 거친 밉의 상주 페이지** 를 가리켜 폴백이 자연히 된다. 텍스처 하드웨어가 알맞은 밉·텍셀을 골라 준다.

여기서 메모리 문제가 나온다. 스케일·바이어스는 16비트 이상 정밀도가 필요해 FP32 4성분이 단순한 선택이다. 직접 계산하면 가상 1024×1024 페이지에 밉 사슬 포함 `1024² × 16 B × 4/3 = 21.33 MiB` 가 된다(논문과 일치). 논문의 절충은 테이블을 둘로 나누는 것이다. 가상 페이지마다 물리 페이지 (x, y) 2바이트만 담은 밉 텍스처(`1024² × 2 B × 4/3 = 2.67 MiB`)와, 물리 페이지마다 스케일·바이어스를 담은 작은 FP32 텍스처(보통 32×32)다. 메모리는 8배 줄지만 **의존 텍스처 읽기 한 번이 늘어난다**. 논문은 번역 방식 다섯 가지를 세 GPU 세대에서 재어 표로 보였다. 가장 느린 구세대 카드는 1280×720 전면 쿼드에서 1.08~1.52 ms, 가장 빠른 카드는 0.26~0.37 ms 다. 서로 다른 시기의 하드웨어라 지금 기준으로 읽으면 안 된다.

### 피드백: 무엇을 올릴지 알아내기

장면을 렌더링하면서(또는 별도 저해상도 패스로) **버퍼에 가상 페이지 좌표·희망 밉·텍스처 ID** 를 쓴다. 깊이 테스트를 통과한 보이는 픽셀만 기록하므로 가려진 페이지를 요청하지 않는다. 논문은 렌더 해상도의 10배 작은 버퍼도 눈에 띄는 문제가 없다고 한다. 이 버퍼를 분석해 중복을 걷어내고 우선순위를 매긴다.

- 희망 밉과 현재 상주 밉의 차이가 클수록 우선.
- 같은 페이지를 요청한 샘플이 많을수록 우선.

분석은 CPU(해시 테이블로 부모 페이지 탐색, 80×60 버퍼에 0.5 ms 정도)나 GPU 에서 한다. 한 프레임 늦은 데이터를 써도 괜찮다. 알파 테스트·투명 면, 한 면에 소스가 여럿인 경우는 피드백이 불안정해지므로 **체커보드 패턴** 으로 소스를 번갈아 요청하는 우회가 소개된다.

### 상주 갱신 파이프라인

우선순위 순서로 캐시에서 압축 데이터를 꺼낸다(없으면 비동기 로드). 물리 페이지를 할당하고, **먼저 매핑을 해제**해 GPU 가 거친 부모 페이지로 내려가게 하고, 트랜스코드(디스크의 가변 비트율 포맷에서 GPU 의 DXT 로)를 마친 뒤에야 새 매핑을 올린다. 교체 정책은 먼저 LOD(세밀한 밉이 먼저 쫓겨남), 그다음 LRU 다. 가장 거친 밉 페이지는 **고정(pin)** 해 두어 시점이 갑자기 바뀌어도 폴백이 있게 한다.

### 과구독과 팝핑

- **과구독**: 보이는 페이지가 풀보다 많으면 스래싱이 난다. 논문은 직전 프레임에서 필요했던 상주 페이지 수를 상·하한선과 비교해 **피드백 LOD 바이어스** 를 올리거나 내린다. 전체가 약간 흐려지는 대신 스래싱을 피하고, 여유가 생기면 되돌린다.
- **LOD 스냅(팝핑)**: 페이지가 늦게 도착하면 세밀한 밉이 갑자기 나타난다. 논문의 해법은 세밀한 페이지가 오기 전 거친 밉을 **업샘플한 임시 페이지** 를 먼저 올리고, 진짜 페이지가 오면 색만 서서히 섞는 것이다.

### 필터링의 불편함

텍스처 유닛은 페이지 경계를 모르므로 이웃 가상 페이지가 물리적으로 멀리 있다. 쌍선형이 정상 동작하려면 페이지에 **테두리 텍셀** 이 있어야 하고, 이방성 필터링은 테두리가 1텍셀보다 넓어야 하며 4텍셀을 쓴다. 이 테두리는 논문 계산으로 텍셀의 약 12% 를 더 쓴다. 직접 계산하면 `120²/128² = 87.9%` 이므로 12.1% 가 낭비다. 삼선형은 두 번 번역하거나(비싸다) 물리 풀에 한 밉을 더 저장(25% 메모리 증가)해야 한다.

## 현재의 변종(요약)

Epic 문서는 두 가지로 나눈다. **스트리밍 가상 텍스처(SVT)** 는 디스크에 구운 텍셀 데이터를 필요할 때 읽고(큰 아트 텍스처, 라이트맵, UDIM), **런타임 가상 텍스처(RVT)** 는 GPU 가 런타임에 텍셀을 만들어 캐시한다(지형 머티리얼 합성, 데칼 블렌딩). 문서는 SVT 가 밉 기반 텍스처 스트리밍의 대안이며 큰 크기에서 메모리 부담이 적다고 한다. 구현 세부(타일 크기 등)는 문서에 없어 확인하지 못했다.

## 언제 쓰나

- 지형·건물군처럼 **크고 반복 없는 텍스처** 를 쓰는 개방 세계.
- 라이트맵, UDIM 같은 큰 아틀라스형 데이터를 상주 비용 없이 쓰고 싶을 때.
- 지형 머티리얼 합성·데칼 블렌딩처럼 런타임에 텍셀을 만들어 캐시하는 RVT 용도(Epic 문서).
- 장면의 텍스처 상태 전환이 많아 배칭이 막힐 때(논문이 드는 효과).

## 주의/비용

- **번역 비용과 의존 읽기.** 모든 샘플에 페이지 테이블 읽기가 추가된다. 품질 필터링(삼선형·이방성)은 번역을 늘린다.
- **필터링 복잡도.** 테두리 12% 낭비, 삼선형 비용, 이방성 파생 계산 문제. 하드웨어 스파스 지원이 있어도 경계 필터링 문제는 따로 확인해야 한다(이 논문은 하드웨어 지원이 없는 경우를 다룬다).
- **첫 장면 품질.** 시점이 갑자기 바뀌면 거친 밉이 보인다. 팝핑 완화·고정 페이지가 필요하다.
- **피드백 지연.** 논문은 한 프레임 묵은 피드백을 써도 된다고 하지만, 시점이 급변하면 올라오기 전까지 폴백 밉이 보인다.
- **알파·투명·다중 소스는 불안정.** 체커보드 같은 보정이 필요하고 작은 면은 과소 샘플될 수 있다.
- **트랜스코드 부하.** 가변 비트율에서 DXT 로 변환하는 일이 상당한 CPU 부하이며, 논문은 프레임당 8~16 페이지를 변환하는 상황에서 128×128 페이지 16개를 60 Hz 로 처리하면 약 15 MT/s 라고 계산한다.
- **튜닝 대상이 늘어난다.** 페이지 크기(논문은 128 을 합리적 절충이라 함: 작을수록 테두리 낭비·페이지 테이블 증가, 클수록 안 보이는 텍셀을 끌어옴), 풀 크기, 피드백 해상도, LOD 바이어스 범위.
